
This chapter presents the empirical results from the benchmark as described in Section \ref{sec:measurement}. The results cover handshake latency, message sizes, and memory footprint for each of the nine evaluated variants: classical WireGuard, four ML-KEM variants (hybrid and pure, at NIST security levels 3 and 5), and four HQC variants (hybrid and pure, at NIST security levels 3 and 5). The results are then used to answer the research questions posed in Section \ref{research_questions} and to draw comparisons with the related work.

\subsection{ML-KEM}
A surprising result in the latency data shown in Table \ref{tab:LatencyPercentiles} was that both pure ML-KEM variants had a faster handshake time than classical WireGuard across all measurements. Pure-MLKEM-768 is approximately 36\% faster, and Pure-MLKEM-1024 about 21\% faster. 

This result seems counterintuitive at first, as a handshake with larger messages is not expected to be faster than the classical baseline. The exact cause of this advantage cannot be isolated with certainty from the total handshake time measured in this benchmark. Two possible explanations are considered below.

The first is algorithmic: Although both algorithms operate on fixed-size inputs, their computational structure differs substantially. ML-KEM primarily performs arithmetic on small polynomial coefficients using Number-Theoretic Transforms (NTT) \cite{mlkem}, whereas X25519 performs a constant-time Montgomery ladder over a 255-bit prime field \cite{rfc7748}. Because of this, ML-KEM might simply have a lower computational cost in this implementation than X25519. Furthermore, ML-KEM's computations contain more independent arithmetic operations, while the Montgomery ladder used by X25519 has long chains of data dependencies. On modern superscalar processors, workloads with greater instruction-level parallelism can execute more efficiently.

The second is implementation-related: The ML-KEM implementation from liboqs is written in C, whereas X25519 is implemented using Go's cryptographic library. Differences in programming language, compiler optimizations, and implementation strategies could have influenced performance independently of the underlying algorithms.

Distinguishing between these explanations, or quantifying each one's contribution, would require isolating pure cryptographic computation time from network and reassembly overhead through dedicated microbenchmarks, which falls outside the scope of this thesis. 

Neither implementation benefited from AVX2 acceleration in this benchmark as the VMs CPUs did not support it. Both algorithms therefore ran in their portable, non-accelerated form, and the result should not be assumed to hold on hardware where either implementation could use an AVX2-optimized code path instead.

The hybrid ML-KEM variants, however, are slower than both the classical handshake and the pure-KEM variants. Hybrid-MLKEM-768 has a mean of \qty{2.228}{ms} and Hybrid-MLKEM-1024 has a mean of \qty{2.374}{ms}, representing handshakes approximately 22\% and 30\% slower the classical baseline respectively. This is expected since the hybrid mode keeps all the existing DH operations from the classical handshake and adds a full KEM encapsulation and decapsulation on top.


\subsection{HQC} 
The HQC results are in a completely different performance category. Pure-HQC-192 has a mean handshake time of \qty{364}{ms} and Pure-HQC-256 even reaches as high as \qty{668}{ms}. The hybrid variants are faster but still far outside any acceptable range: Hybrid-HQC-192 takes \qty{202}{ms} and Hybrid-HQC-256 takes \qty{366}{ms}. 

The main cause of this latency is not HQC's computational cost but the IP fragmentation and software reassembly forced by its large message sizes. HQC's public keys and ciphertexts are large enough that every HQC handshake message must be split into multiple IP fragments before transmission. As described in Section \ref{sec:benchmark}, the virtual network path in this benchmark handles fragmentation and reassembly entirely in software, without hardware offloading. The operating system must buffer all incoming fragments, wait for the final fragment to arrive, and then reassemble the complete datagram before WireGuard can begin processing the message. This reassembly overhead grows with the number of fragments and is the primary driver of the observed latencies, consistent with the fragment counts discussed in Section \ref{sec:results-fragmentation}. 

The standard deviations shown in Table \ref{tab:Results} for the HQC variants further support this explanation. Pure-HQC-192 has a high standard deviation of \qty{14.3}{ms} and Pure-HQC-256 has \qty{23.5}{ms}, compared to a standard deviation of less than \qty{0.35}{ms} for all ML-KEM variants. Key generation, encapsulation, and decapsulation complete in a consistent amount of time and are executed locally, so if these operations dominated the total handshake time, all variants would show similarly low variance regardless of message size, as is the case for ML-KEM. The elevated variance in HQC instead reflects the reassembly process itself: because reassembly cannot complete until the last fragment arrives, its duration is subject to per-fragment scheduling and arrival jitter that accumulates as fragment count increases. This is consistent with Pure-HQC-256 requiring more fragments than Pure-HQC-192 and correspondingly showing higher standard deviation, reinforcing that reassembly overhead, rather than KEM computation, is the dominant contributor to the observed latency.

\section{Message Size}
Table \ref{tab:Results} shows a large variance in the message sizes across the nine variants. To understand where these sizes come from, it helps to look at the individual fields that make up each message.

\subsection{Initiation Message Fields Breakdown}

A fixed overhead of \qty{84}{bytes} is identical across all nine variants, as the fields it covers are independent of the choice of algorithm. As illustrated in Figure \ref{fig:wg-initiation}, these fields are the 4-byte message type, the 4-byte sender index, the 28-byte encrypted timestamp with its authentication tag, and the two 16-byte MAC fields used for denial-of-service resistance.

The three remaining fields differ considerably between the modes. In the classical handshake the initiator sends only its 32-byte Curve25519 ephemeral public key and a 32-byte encrypted version of its static Curve25519 key, for a total of 148 bytes. For the hybrid variants, the ephemeral key field is extended by appending the KEM ephemeral public key directly after the classic Curve25519 key, and the static field remains a 32-byte Curve25519 key because authentication still relies on the classical identity.

The fixed portion accounts for 60 bytes: the 4-byte message type, 4-byte sender index, 4-byte receiver index, 16-byte empty encrypted payload with its authentication tag, and the two 16-byte MAC fields.

In the hybrid modes, described in Section \ref{sec:method-hybrid}, the responder keeps its Curve25519 ephemeral key and additionally sends the KEM ciphertext \texttt{ct\_ee}, which encapsulates a shared secret to the initiator's ephemeral KEM public key.  

Because the classical DH exchange has been removed entirely, the pure-KEM response contains no Curve25519 ephemeral key. Instead, the responder encapsulates a fresh shared secret to the initiator's ephemeral KEM public key, producing the ciphertext \texttt{ct\_ee}, and returns this alongside the fixed overhead fields.

Response messages are consistently smaller than the initiation messages in the pure-KEM modes, by a factor of around two to three depending on the algorithm. This asymmetry arises as the initiator bears the cost of sending its ephemeral public key, the authentication ciphertext \texttt{ct\_es}, and its encrypted static public key, while the responder only needs to return the single ciphertext \texttt{ct\_ee}. In the hybrid modes this asymmetry is noticeably smaller, since both messages carry only a Curve25519 ephemeral key alongside a single KEM component.

Among the benchmarked post-quantum variants, Hybrid-MLKEM-768 is the only one that fits within a single packet in both directions, matching the classical handshake in total packet count. The HQC variants tell a very different story: both the initiation and response messages require multiple fragments. Even the hybrid HQC variants are heavily fragmented in the response direction because the large HQC ciphertexts must be transmitted. The handshake latency results in Table \ref{tab:LatencyPercentiles} are a direct consequence of this fragmentation, and the gap between the ML-KEM and HQC variants in Table \ref{tab:Fragments} mirrors the gap observed in latency.

\section{Comparisons With Related Work}\label{sec:results-comparisons}

\subsection{PQ-WireGuard}
Hülsing et al.\ report a client-side handshake time of around \qty{1.0}{ms} over a virtual \qty{10}{Gbps} link with no added latency \cite{pqwg}, which is in the same order of magnitude as the pure ML-KEM variants in Table \ref{tab:LatencyPercentiles}. PQ-WireGuard fits both handshake messages within the \qty{1232}{byte} IPv6 budget, which the pure ML-KEM variants in this thesis do not achieve, as shown in Table \ref{tab:Fragments}. The Classic McEliece parameter set used produces a static public key of \qty{512}{KB}, which, at \num{10000} peers amounts to approximately \qty{5}{GB} for the peer table, compared to roughly \qty{11}{MB} for pure ML-KEM-768 at the same scale (cf. Table \ref{tab:StaticStorage}).

\subsection{Rosenpass}
A direct latency comparison with Table \ref{tab:LatencyPercentiles} is not meaningful for Rosenpass \cite{rosenpass}, since it operates as a separate sidecar process whose cryptographic cost must be added to WireGuard's handshake time. Rosenpass fits both its InitHello and RespHello messages within a single IPv4 packet. Out of the variants in this thesis, only Hybrid-MLKEM-768 achieves a comparable result (Table~\ref{tab:Fragments}).

\subsection{Rebar}
Rebar \cite{rebar} was benchmarked with \qty{30.9}{ms} of added artificial latency and reports a handshake time of approximately \qty{36.9}{ms} for the initiator, compared to \qty{33.6}{ms} for classical WireGuard in the same environment. Its initiation and response messages are \qty{1052}{bytes} and \qty{1088}{bytes} respectively, fitting within the \qty{1472}{byte} IPv4 budget that none of the pure-KEM variants in this thesis achieve.

\section{Research Questions}\label{sec:results-rq} 
This section revisits the research questions posed in Section \ref{research_questions} and answers each one using the results presented above. The goal is to translate the concrete benchmark findings into conclusions about the performance, resource requirements, and practical deployability of ML-KEM and HQC as post-quantum replacements for the classical WireGuard handshake.

\textbf{RQ1: How do NIST-selected post-quantum key encapsulation mechanisms, specifically ML-KEM and HQC, affect the performance of a WireGuard handshake?}

As shown in Table \ref{tab:LatencyPercentiles}, the pure ML-KEM variant completes handshakes faster than the classical baseline on the benchmark hardware. This is likely due to some combination of the lower asymptotic cost of NTT-based lattice arithmetic and differences in compiled implementation efficiency, though this benchmark cannot isolate the precise contribution of each factor.

The hybrid ML-KEM mode adds modest overhead over the classical baseline. HQC produces latencies orders of magnitude above the classical baseline across all four variants, primarily due to IP fragmentation and software reassembly rather than cryptographic computation.

\textbf{RQ2: What impact do ML-KEM and HQC have on resource usage in WireGuard, particularly in terms of message size and storage requirements?}

ML-KEM increases message sizes significantly in the pure-KEM mode, as shown in Table \ref{tab:Results}, but the hybrid ML-KEM-768 variant fits within a single IPv4 packet in both directions. Per-peer static key storage for the pure ML-KEM variants, shown in Table \ref{tab:StaticStorage}, grows substantially compared to the classical case but remains manageable at realistic deployment scales. The HQC variants produce significantly larger messages and require greater storage capacity at all parameters. 

This storage overhead is modest next to Classic McEliece-based approaches such as PQ-WireGuard, whose \qty{512}{KB} static keys impose a per-peer storage burden one to two-and-a-half orders of magnitude larger than the pure KEM variants of this thesis (cf. Section \ref{sec:results-comparisons}).

\textbf{RQ3: To what extent can ML-KEM and HQC be integrated into WireGuard without violating its core design principles, such as low latency and small handshake size?}

Hybrid-MLKEM-768 is the only post-quantum variant that preserves WireGuard's single-packet handshake under IPv4. The pure ML-KEM variants require a small number of fragments but remains computationally fast. HQC cannot be integrated without significantly violating WireGuard's design principles: the messages require heavy fragmentation and the resulting latencies shown in Table \ref{tab:LatencyPercentiles} are impractical. 

\textbf{RQ4: How do hybrid cryptographic approaches compare to purely post-quantum approaches in terms of security, performance, and deployability?}

The hybrid approach preserves classical security as a fallback and provides post-quantum forward secrecy, but does not achieve full post-quantum authentication. The pure-KEM approach provides both. As shown in Table \ref{tab:LatencyPercentiles}, the pure ML-KEM mode is faster than the hybrid mode on this hardware because it replaces rather than augments the classical operations, though this result is hardware-dependent. 

The hybrid mode is more deployable right now because it does not require distributing new static KEM public keys for all peers and can be integrated without replacing the existing static key infrastructure.

\textbf{RQ5: How does a hybrid WireGuard implementation using ML-KEM and HQC compare to existing post-quantum solutions in terms of performance and practical deployment?}

Compared to Rosenpass, the in-handshake integration in this thesis completes post-quantum key establishment within a single WireGuard handshake rather than requiring a separate process, and the pure-KEM variants achieve full post-quantum authentication that Rosenpass does not provide. The cost is a higher deployment barrier, since the integration requires modifying WireGuard's codebase, and larger initiation messages compared to Rosenpass.

\textbf{RQ6: What trade-offs exist between security level and ciphertext size when selecting PQC algorithms for use in WireGuard?}

For ML-KEM, moving from NIST security level 3 to level 5 increases message sizes and per-peer storage moderately, as shown in Tables \ref{tab:Results} and \ref{tab:StaticStorage}, and adds a small amount of latency visible in Table \ref{tab:LatencyPercentiles}. The handshake remains practical at both levels. For HQC, the same step produces a much larger increase in both message size and latency, making an already impractical result considerably worse. For WireGuard specifically, where message size is a hard constraint, the level 3 to level 5 upgrade is manageable with ML-KEM but effectively prohibitive with HQC.
